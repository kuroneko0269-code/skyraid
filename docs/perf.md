# 性能と容量（8-2・10-1）

本番ビルドの容量と読み込み量の記録。クラウドのセッションはソフトウェア描画（SwiftShader）なので **fps は評価しない**。時間と Lighthouse のスコアは **クラウドでの参考値**（同じ環境での前後比較にだけ使う。実機の値ではない）。

## 計測の手順

```
npm run perf                                   # 本番ビルド → node scripts/perf.js perf-report
node scripts/perf.js <出力先> --dir <dist> --runs 9   # 別の dist（変更前のビルドなど）を測る
```

`scripts/perf.js` は dist を `dist/_headers` のヘッダー付きで配信し（`scripts/serve-dist.js`）、Playwright の Chromium（844×390・タッチ）で次を測る。結果は `<出力先>/perf.json`。

| --- | --- |

## チャンクの分け方（推奨案 A を採用）

| 案 | 内容 | 長所 | 短所 |
| --- | --- | --- | --- |
| **A（採用）** | 起動時のモジュールだけを `three-core`・`three-webgl`・`game`・`render`・`app` に分ける（`scripts/vite-chunks.ts`） | どれも 500KB 未満で上限を変えずに警告が消える。three はデプロイをまたいでキャッシュが効く。起動時の CSS は 1 ファイルで並びも同じ | 起動時の要求が 2 → 6（HTTP/2 で並行。index.html が全部を最初から読む） |
| B | three を 1 つの vendor チャンクにし、`chunkSizeWarningLimit` を 600KB に上げる | 要求は 3 つで済む | 警告を黙らせるだけ。アプリのチャンクが 650KB 台で残る |
| C | Rolldown に任せる（groups なし） | 設定なし | 遅延チャンクと共有するモジュールが 1〜40KB の共通チャンクと CSS に細かく切り出された（起動時の要求が 10 本以上、CSS の並びが変わる） |

## 見つかったこと
